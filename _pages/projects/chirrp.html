CHIRRP: Hydro-AI for Participatory Water Planning

Stakeholders ask a groundwater question in plain language and get an instant, physics-based answer they can audit against the numerical model it replaces.

My role

I led the technical build. I trained and validated the physics-informed surrogate against MODFLOW-2005, built the web application, and connected the LLM layer, which parses requests and retrieves regulations, to the surrogate and the app. The paper is led by my advisor, Dr. Ruopu Li.

Problem

Groundwater planning decisions such as how much to pump, and where, involve people who don't run numerical models. Each "what if" normally means a modeler setting up and running MODFLOW, so stakeholders see a few pre-chosen scenarios instead of exploring the trade-offs themselves.

Approach

CHIRRP couples two layers:

  • Social layer: an LLM parses a plain-language request ("reduce pumping by 15%") into a validated scenario object, with a regex fallback, and retrieves relevant Nebraska groundwater regulations through retrieval-augmented generation.
  • Physical layer: a physics-informed neural network (PINN) surrogate of transient groundwater drawdown returns the full head field in a fraction of a second. Any result can be checked against a live MODFLOW-2005 run.
  1. Plain-language requesttext or voice
  2. LLM scenario parsingvalidated, in-envelope only
  3. PINN surrogatefull space–time head field
  4. MODFLOW cross-checkon demand
  5. Decision readoutmaps, comparisons, regulations

End to end, an interaction takes about 5.7 s, and the two LLM calls dominate. The hydrology is not the bottleneck.

The application

  • Explore: ask a scenario and get head and drawdown maps with a plain-language readout.
  • Compare: overlay 2–4 pumping plans and flag the lowest-impact valid option.
  • Find Limits: set a tolerable drawdown and search the trained envelope for the maximum allowable pumping (500 options in 256 ms).
  • Accuracy: surrogate vs. MODFLOW metrics computed live.

Engineering: a FastAPI backend and Angular UI ship as a single Docker container on Hugging Face Spaces, with Postgres/pgvector for retrieval and LangGraph for scenario parsing. A reproducibility map ties every number in the paper to the file that produces it.

Scope and limitations

  • Single-well, homogeneous-aquifer scope. Requests outside the trained envelope (−37.5% to +25% of baseline pumping) are rejected, not extrapolated.
  • Not yet evaluated with real stakeholders.
  • The deployed app runs CPU inference; the GPU path exists but isn't used in production.
